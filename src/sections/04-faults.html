Supported faults

Every fault can be injected in two ways. Pick one to see the examples:

Write a command to the FIFO while your system runs: you decide when the fault happens.

Declare [[injection]] entries before mounting: LazyFS fires them at a precise call, e.g. “the 2nd group of writes to log.txt”.

Lost writes

clear

Drops every unsynced write but keeps LazyFS running. You kill and restart your system, which is ideal for Jepsen-style tests that crash processes themselves.

echo "lazyfs::clear-cache" > /tmp/faults.fifo
[[injection]]
type="clear-cache"
from="/tmp/lazyfs.root/wal.log"
op="fsync"
timing="after"
occurrence=3

Crash

crash

Drops unsynced data and kills LazyFS right before or after a system call on a given file. Crashing before LevelDB renames 000002.dbtmp leaves a database that cannot start (bug #3).

echo "lazyfs::crash::timing=before::op=rename::from_rgx=dbtmp" > /tmp/faults.fifo
[[injection]]
type="clear-cache"
from="/tmp/lazyfs.root/000002.dbtmp"
to="/tmp/lazyfs.root/CURRENT"
op="rename"
timing="before"
occurrence=1
crash=true

Linear torn write

torn-seq · torn-op

Only the beginning of the data reaches the disk, e.g. the first half of a large write, or the first 2 of 4 writes. Only the first half of etcd's 16 KiB snapshot write: “invalid database” on restart (bug #16).

echo "lazyfs::torn-op::file=/tmp/lazyfs.root/member/snap/db::persist=1::parts=2::occurrence=1" > /tmp/faults.fifo
[[injection]]
type="torn-op"
file="/tmp/lazyfs.root/member/snap/db"
parts=2
persist=[1]
occurrence=1

Non-linear torn write

torn-seq · torn-op

Later data reaches the disk without the data before it, e.g. the 4th write but not the 3rd. ZooKeeper with its 4th log write but not its 3rd: CRC error on startup (bug #8).

echo "lazyfs::torn-seq::op=write::file=/tmp/lazyfs.root/log.txt::persist=1,4::occurrence=2" > /tmp/faults.fifo
[[injection]]
type="torn-seq"
op="write"
file="/tmp/lazyfs.root/log.txt"
persist=[1,4]
occurrence=2

Both torn writes can be injected on a sequence of writes to a file (torn-seq: choose which writes persist) or on one large write split into parts (torn-op: choose which parts persist). In both cases LazyFS crashes right after.

Helpers

  • lazyfs::unsynced-data-report: what would be lost right now.
  • lazyfs::cache-checkpoint: write all unsynced data to ext4.
  • lazyfs::display-cache-usage: how full the cache is.
  • Log parser: turn on log_all_operations, then logparse/parse.py turns the log of every system call into a graph, showing where to inject faults.
